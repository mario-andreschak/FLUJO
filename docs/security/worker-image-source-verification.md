# Verifying the source behind worker image labels

The worker image contract uses `io.flujo.worker.snapshot-envelope-read-versions="1,2"` and the canonical six-field `io.flujo.worker.snapshot-default-limits` JSON from [the image snapshot contract](worker-image-snapshot-contract.md). `io.flujo.worker.snapshot-source="1"` remains the separate private-source capability. Snapshot format 2, layout 2, protocol 1 and an application version cannot substitute for these checks.

Both image candidate workflows run `node scripts/worker-image-capability.mjs generate "$GITHUB_SHA"` before Docker builds. The helper executes the selected native TypeScript metadata, envelope codec and limits function in an isolated child process. It removes only `FLUJO_SNAPSHOT_MAX_FILE_BYTES` and `FLUJO_SNAPSHOT_MAX_BYTES` in that child to measure defaults, supplies the full build revision, and compares the actual source advertisement and canonical defaults to the reviewed image contract. It independently constructs authenticated v1 and v2 envelopes, exercises both native reads and wrong-key refusal, and independently decrypts a new native v2 write. Generation also compares the actual Dockerfile runtime labels, including source capability 1, to the source result.

For a revision-labelled build, the Docker builder repeats the source check before the application build. This check reads the native modules copied into the build context, without requiring `.git` or the Dockerfile excluded by `.dockerignore`. An empty revision returns `qualified: false`; it does not qualify a local image for worker selection. The existing immutable-image inspectors still require the full source identity and all compatibility labels. Signing and promotion use the static reviewed label contract and retained evidence; they do not execute the application source probe. Registry readback rechecks every required label before alias writes.

The helper reports hashes of the actual source files and package metadata. These are source controls, not a compiled-image revision proof, installed transactional restore, private credential consent, cross-process lease acceptance or effective target configuration. Any runtime limit override requires separate target qualification. A companion must bind all six effective target limits to the selected immutable image/configuration and compare them with the source's configured limits before capture. The default label cannot establish a target's overridden values.

The release-safety image contract tests include the source controls. They mutate each default bound, advertised versions, the actual reader, authentication purpose, new writer and Docker labels. They also mutate retained evidence and immutable registry readback, checking that refusals prevent alias writes. The installed worker smoke expects source capability 1 alongside native v2 metadata and the existing default-limits comparison. Its execution remains a separate installed-image gate.
