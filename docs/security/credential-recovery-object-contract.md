# Encrypted credential recovery objects

This successor builds on frozen #747 (`cdeed858df15ca6e8707b99fde3fa0cbc1a5bd28`). It supplies the authenticated object and private manifest formats needed by an explicit credential migration. These formats have no production caller yet: they do not create a filesystem journal, block ordinary credential operations, rotate the active key or convert records. The accepted #567 migration and A- remain open.

The source control uses real temporary storage, real metadata initialization and real AES-GCM while modeling process/runtime lock admission. It creates DEFAULT metadata under the published `FLUJO~` password, calls today's `initializeEncryption(privatePassword)`, and observes USER metadata with the same `key_id`. A copy of the original DEFAULT metadata unwraps the same active key and decrypts a new credential subsequently encrypted with the private password. Changing the wrapping password alone therefore does not retire that exposed data key. The source fixture is not an installed application or a cross-process qualification.

`credentialRecoveryFormat.ts` defines `flujo-credential-recovery` version 1. Each object uses AES-256-GCM, a fresh 12-byte nonce and a separately supplied 32-byte recovery key. AAD binds the workspace, canonical UUIDv4 transaction ID, manifest/before/after role and exact fixed store name. The closed wire schema bounds input before JSON parsing, requires canonical base64, and authenticates before returning owned plaintext bytes. Each crypto operation clears its owned key copy and any unauthenticated plaintext emitted before GCM finalization; the retained caller key remains unchanged. This does not establish independent entropy, operator retention or complete memory erasure, including JavaScript strings.

The five core files are `encryption_key.json`, `models.json`, `registry_account.json`, `global_env_vars.json` and `mcp_servers.json`. An individual before/after object is limited to 8 MiB of plaintext and a manifest to 64 KiB. Original bytes are opaque: legacy ciphertext, plaintext, extension fields and corrupt binary input can be backed up exactly without parsing, repairing, erasing or making a plaintext corruption copy. A later preflight must refuse unsupported or corrupt records before changing active storage.

The manifest encrypts the complete ordered inventory, original/target byte lengths and SHA-256 witnesses, source/target key IDs and transaction phase. Hashes of potentially low-entropy plaintext never appear in a public status DTO or sidecar. Its parser rejects missing/duplicate/reordered stores, unknown fields, identity substitutions, invalid bounded witnesses, removal of a present store and an absent target key file. A v1 source may have no v2 key ID. The target ID must differ from the source ID, but the manifest parser alone cannot prove that either ID was derived from real key metadata or that a new random key exists. The trusted preparation driver must derive and verify both identities.

Phase transitions allow prepared → committing or rolling-back, repeated committing/rolling-back for explicit recovery, committed → rolling-back and rolling-back → rolled-back. Rolled-back is terminal; another forward migration requires a new transaction. Authenticated but malformed manifest data is refused with the same fixed recovery diagnostic as unauthenticated data. Raw JSON, ciphertext, parser messages, abort causes, paths and secret content are not included in these errors.

Three selected Node source suites pass 23 tests, zero failures and zero pending tests using the verified official Node 22.23.3 binary. The receipt is `.tmp/credential-recovery-supported-qualified.json`. The fixtures cover real encryption/decryption, unknown-extension hiding, opaque corrupt bytes, fresh nonce/caller-key preservation, key and identity replay denial, closed schema and wire tampering, separate bounds, legal phase transitions, authenticated malformed manifests and the real copied-public-metadata rewrap control. Changed-file lint and diff checks pass. The initial smaller default-runtime receipts remain retained; no installed server, provider, OCI image, browser, crash/restart or external reassessment was exercised.

Integration still requires complete flows/runtime-home/bootstrap inventory, independent external recovery-key retention, encrypted immutable before/after persistence and readback, a durable pending marker, an actual new random active key and authenticated conversion of every accepted record, conflict checks, resume/rollback, credential-effect generation admission across processes, visible commit after cache/refresh invalidation and installed Linux/Windows qualification. The five core files are not the complete #567 inventory. Ordinary credential-free exports and the remaining #566/#568 topics remain separate open work. Preserve existing legacy reads, native ownership guards, combined-root consent/leases and the original provider/model SDK source blobs during selective intake.
