# Exclusive workspace recovery writes

This successor builds on the frozen #745 image contract, `d01e095fc6bf9d25d91e78ce423c99c307b10b09`, and #736's live nested mutation leases. It adds `withWorkspaceRecoveryMutation(task, {workspace?, timeoutMs?, signal?})` for a future journaled recovery transaction. No HTTP route, credential migration, active-key replacement, journal or backup is integrated here.

Ordinary `runInWriteChain`, storage and runtime-lock writes enter `withWorkspaceMutation`. A read-only recovery capture holds admission closed; awaiting one of those writes from inside the capture would wait behind its own boundary. The new API explicitly drains existing registered writes, holds the existing physical cross-process snapshot admission and supplies one live mutation lease for its selected workspace. Nested ordinary storage/queue calls borrow that lease and check the physical owner before entering their task. Outsiders retain normal admission and wait behind recovery. `withWorkspaceRecoveryCapture` remains a read capture and supplies no write bypass.

The frozen operation exposes `workspace`, `generation` and `assertOwned()`. The generation is the existing in-process capture counter, not a durable credential/effect generation, transaction ID or key version. The ownership check requires a live lease, the originally selected cancellation signal and matching workspace, and checks state again after awaiting the actual physical owner. The original signal is captured so later caller mutation of the options object cannot remove cancellation. The public operation retires after all started participants settle. An inherited retired recovery context refuses `RECOVERY_FINISHED` rather than turning old staged values into a freshly admitted ordinary write. Independent ordinary callers can still enter after recovery releases its admission.

The owning operation waits for every started nested mutation, even when its root callback fails or cancellation arrives. Cancellation denies new recovery effects and returns a fixed message without the caller's abort reason, including during initial drain/acquisition. It cannot cancel native IO already started; the physical gate remains held until started tasks settle. The existing local snapshot boundary may unblock on abort, but the unchanged physical process gate still excludes ordinary effects until release. Ownership is checked again before acknowledging completed recovery effects. If ownership is lost after a write, refusal does not undo that write; the future durable journal must recover it.

Recovery ownership/workspace/retirement/cancellation refusals have fixed diagnostics without raw cause. Caller business-task failures and non-cancellation initial admission failures retain the existing behavior; any public migration route must sanitize its response separately. The existing cross-process lock protocol remains responsible for process birth identity, conditional dead-owner retirement, FD/dev/inode/nanosecond/mode/uid/single-link ownership and release. No such guard is changed, and arbitrary unregistered writers or older nonparticipating processes remain outside its coverage.

Focused source tests model process admission/ownership and exercise a real native filesystem `runInWriteChain` → `writeFileAtomic` journal-state write under the exclusive lease, followed by an outsider write after release. They check initial writer drain, root success/failure with nested work, retired descendants, original-signal retention, cancellation before entry/during drain/after awaiting ownership/with already-started work, fixed ownership failure, final ownership acknowledgement, foreign/explicit workspace scope, late public ownership-check retirement, read capture without a write bypass and refusal inside a live ordinary mutation. The physical atomic writer and all its metadata checks are real and unchanged; only process admission/ownership is modeled. The fixture uses synthetic state, its owned temporary directory is observed empty of staging files and removed. This is not an installed application, real physical cross-process admission, credential conversion or crash/resume receipt.

Four selected Node suites pass 43 tests, zero failures and zero skips: 16 new recovery admission assertions, 9 existing mutation lifetime assertions, 13 coordinator assertions and 5 actual authenticated transfer route assertions. Receipt: `.tmp/exclusive-recovery-write-qualified.json`. Changed-file lint and diff checks pass. The initial fixture run had five failures from matching absent/non-enumerable Error properties with an object matcher; the fixtures now assert `.code`, `.message` and `.cause` directly. That initial receipt is preserved at `.tmp/exclusive-recovery-write-initial-fixture.json`; no production error property or diagnostic was weakened to satisfy the tests. Hosted full app/MCP types/business and installed verification remain pending.

These guards are a prerequisite, not a complete #567 migration. Integration still requires authenticated inventory, independently retained encrypted recovery backup, new random active key rather than same-key rewrap, staging/integrity checks, durable pending journal and credential-effect generation admission across processes, atomic visible commit, cancellation/crash recovery, resume/rollback, cache/refresh invalidation, legacy/mixed record preservation and installed Linux/Windows qualification. Add the future transaction outside any ordinary write admission or per-key chain; otherwise it can deadlock on the admission it needs to drain. Preserve the combined root's later consent/lease protections and the original eight provider/model SDK source blobs during selective intake. Ordinary export filtering, browser pairing/default isolation, human/external reassessment and the accepted A- remain open.
