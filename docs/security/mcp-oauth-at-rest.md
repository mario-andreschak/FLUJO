# MCP OAuth writes at rest

This source slice follows #720 at `c6328fd404a87db04ce90333f23d7f6c37a608b7`. Previously the MCP OAuth provider stored access/refresh tokens, arbitrary token extensions, dynamically registered client secrets and PKCE verifiers directly in `mcp_servers.json`. Log redaction did not encrypt those values.

New provider saves wrap the complete SDK value in `{format: 'flujo-oauth-v1', ciphertext: 'v2:…'}` using the current workspace key through the existing authenticated AES-256-GCM writer. The authenticated plaintext includes the envelope version, OAuth purpose (`tokens`, `client` or `verifier`), owning workspace and the complete JSON value. Access/refresh/ID tokens, nested provider extensions, numeric extension values, registration metadata and private JWKS therefore remain inside ciphertext. Registration metadata is retained in that encrypted value; the old separate `oauthClientMetadata` copy is removed on a successful new registration save. The provider's locally constructed `clientMetadata` remains available to the SDK.

SDK getters unwrap only on the backend. The service status reader uses the same token reader so an expired access token with a refresh token retains reconnect readiness. Transport setup checks stored-value presence without interpreting an envelope as an access token. Invalidations remove either stored representation. New envelope reads require the current workspace to be unlocked, authenticate the ciphertext and check the embedded purpose/workspace before returning a validated SDK value. Historical plaintext also requires an unlocked workspace, including manually registered client secrets, but remains readable without an automatic rewrite. Historical provider extension fields named `format` or `ciphertext` are preserved when they are part of a normal SDK object; the owned format marker and the two-field envelope shape are reserved.

New saves validate the serialized representation before encryption and accept at most 256 KiB of serialized plaintext; reads bound ciphertext admission to 512 KiB and decrypted text to 256 KiB. These are acceptance bounds, not a streaming JSON serializer or a bound on all allocations before serialization. Unknown extension fields are retained inside ciphertext. Parser, crypto and storage failures produce fixed provider diagnostics without a raw cause. A failed encryption or unacknowledged persistence leaves the previous active and persisted credentials intact.

The fresh-profile inventory now recognizes the actual model field `ApiKey`, in addition to `apiKey`. A historical plaintext model credential without key metadata refuses fresh enrollment, reports recovery required and retains the original model file. This four-store guard is not the full credential migration inventory.

## Source evidence

The predecessor tests run against the actual #720 source reproduced five failures across the new OAuth/private-profile controls; the existing controls passed, with one native POSIX permission check pending on Windows. The actual stored OAuth values were plaintext, locked reads/writes could bypass encryption, a copied plaintext token remained usable in a different workspace, and the historical uppercase `ApiKey` allowed replacement metadata. Receipt: `.tmp/oauth-at-rest-predecessor.json`.

The corrected tests use the real private enrollment/authentication APIs, storage writer, key metadata and crypto. The OAuth at-rest suite writes and reloads the physical credential file, checks absence of complete synthetic secret values (including nested/numeric extensions and a registration JWK), round-trips all SDK getters, exercises locked reads/writes and legacy/manual lock checks, rejects purpose/workspace substitutions and tampered authentication tags, preserves expired-refresh readiness, validates malformed/oversized refusal, and tests explicit invalidation. The workspace substitution control deliberately copies matching metadata and unlocks the destination with the same key before requiring refusal, so its result tests the embedded workspace binding rather than only a different-key failure. These are source tests with a disposable data root, not an installed browser or external provider qualification.

The existing controlled storage-acknowledgement tests retain their failure, unreadable-store, staged-replacement and log-redaction checks. They now enroll a real private fixture and inspect the decrypted SDK getter after acknowledgement instead of expecting a plaintext storage object. The expired-refresh unit fixture also explicitly enrolls a private workspace. No baseline, assertion-count or skip allowance is relaxed. Final Windows scoped result: seven suites, 58 passed / zero failed / one existing POSIX operator-permission check pending; all 17 new OAuth at-rest controls pass with zero skips. Changed-file lint and diff checks pass. Receipt: `.tmp/oauth-at-rest-qualified.json`; full graph typechecking and installed qualification remain hosted/coordinator gates.

## Remaining scope and compatibility

Private USER profile keys supply confidentiality for these new values. Existing DEFAULT profiles still use the public compatibility password and are not made private by adding this envelope. No historical store is bulk re-encrypted, no new workspace key is rotated, and old backups/exports/runtime homes are not remediated here. The complete #567 migration still needs inventory, encrypted recovery backup, authenticated re-encryption with a new active key, a durable journal, interrupted-writer admission/resume/rollback, and integrity-checked commit. Generic storage and stale concurrent provider refreshes need that migration generation contract; this slice does not claim one.

Ordinary backup/export and browser configuration responses are separate egress boundaries. This branch does not establish credential-free export or browser response allowlists. Intentional worker transfer still needs its separately qualified encrypted recipient contract; existing worker restores retain the manifest workspace identity, while copying a credential to a differently named workspace now requires an explicit authorized re-encryption rather than a blind credential copy. No actual installed worker migration/restore, external OAuth refresh, browser owner pairing, revocation or independent human/external reassessment is claimed. The CodeQL source inventory is in `current-codeql-source-map-2026-10-04.md`; it closes no scanner finding.
