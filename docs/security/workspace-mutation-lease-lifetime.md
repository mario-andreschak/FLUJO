# Workspace mutation admission lifetime

This source slice follows #732 at `ac1c1fe4e6e85f982968d24cfcabce486e01be6a`. The predecessor gate tracked admitted workspace names in AsyncLocalStorage. A descendant retained that set after its owning mutation had settled, so a later call could bypass a newly closed snapshot boundary and the process writer registration. A started nested mutation could also outlive the root callback while the local active count and owning process registration had already been released. Reentrant calls naming a previously admitted workspace ran under the ambient second workspace instead of the explicit target.

Each new admission now owns a live lease. Started reentrant calls retain that lease as participants; the root keeps its in-process admission and existing filesystem writer registration until the root and every started participant have settled, including root failure. The lease then retires. Descendants retaining its async context must obtain fresh admission, so they wait behind a subsequent snapshot boundary and register a new process writer. A reentrant call runs under its explicit normalized workspace. An old HMR context without a live lease grants no inherited privilege.

This changes the lifetime of the existing registered mutation protocol. Started nested writes belong to their owner's operation even when the caller omitted `await`; owner completion now waits for them. Callers must not detach a nested mutation that depends on releasing its owning domain queue or lock. A never-settling participant retains admission and can make captures time out. No timeout is used to release a still-running participant or to declare a process dead. Other processes, birth identity, descriptor/path identity, modes, ownership, single-link checks and conditional recovery remain the existing runtime-lock protocol; none is weakened here.

## Source controls

The frozen predecessor gate blob is `fd64cf9eb4eecae63123d605791c3484dad4e0ef`. Before changing source, four added adversarial controls failed against that exact predecessor: retired-context write admission, early registration release after root success, early release after root failure, and explicit workspace binding. Its three existing in-process tests passed. Receipt: `.tmp/mutation-lease-predecessor.json`.

After the change, nine gate tests and the selected coordinator/route suites pass 27 tests, zero failures and zero skips. Controls verify a retired descendant waits behind a closed boundary and registers afresh; a started nested call retains admission until settlement on root success/failure; explicit cross-workspace reentrancy selects the target; handled child failure releases admission; and capture refuses a live lease but permits a retired descendant. Existing drain/cancellation races remain covered. Receipt: `.tmp/mutation-lease-qualified.json`. Changed-file lint and diff checks pass; no baseline or skip allowance is changed.

The gate tests replace the process registration callback to observe its lifetime deterministically. They do not qualify the physical cross-process protocol, native Windows birth/FD behavior, installed binaries or a complete credential effect fence. Existing process tests and full hosted business checks remain required; no broad local dependency graph, build, container or provider operation is run here.

## Migration still required

This repairs registered write admission; it does not enroll provider calls, cached plaintext, unregistered file writers or stale external OAuth refreshes in a durable credential generation. Credential migration still requires an explicit exclusive recovery-write capability, encrypted recovery backup, fresh active key, authenticated conversion of all accepted legacy formats, durable pending-journal admission on startup and every credential effect, staged integrity validation, atomic visible commit, resume and rollback. Simply writing a journal inside the read capture boundary would deadlock ordinary admitted storage writes. Simply rewrapping metadata retains the old active key and cannot make historical DEFAULT credentials private.

Integration must preserve the combined root's later source consent and process lease protections and qualify queue/lock composition across business consumers. Ordinary exports, browser pairing, isolated execution grants, installed Linux/Windows evidence, human review and external reassessment remain open.
