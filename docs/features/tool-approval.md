# Tool Approval & ChatInput Require Tool Approval Checkbox\n\n## Overview\n\nThe **Require Tool Approval** checkbox in ChatInput is the single, explicit approval gate for tool execution. When enabled, every tool call requires an interactive Approve or Reject decision before execution. When disabled (the default), tool calls execute automatically.\n\n## Single-Gate Design\n\nAs of issue #438, tool approval follows one rule:\n\n- **When Require Tool Approval is checked** (`requireApproval=true`):\n  - Every tool call pauses execution and presents an approval panel.\n  - The user can inspect the tool name and formatted arguments.\n  - Two actions are available:\n    - **Approve** — execute the tool and continue.\n    - **Reject** — return the fixed result `tool denied` and continue.\n  - No rejection reason is captured or sent to the model.\n\n- **When Require Tool Approval is unchecked** (`requireApproval=false`, the default):\n  - All tool calls execute immediately without interruption.\n  - No approval UI is shown.\n\n## No Hidden Policy Layers\n\nThe following are **not** part of the approval decision:\n\n- Persona Behavior rules (backend-only native-ability filtering).\n- Saved \"always allow\" or \"always deny\" decisions.\n- Per-tool `autoApprove` settings.\n- Protected-folder deny rules or bash external-path warnings.\n- Rejection reason feedback to the model.\n- Default approval policies based on tool type, server, or resource path.\n\nAll of the above were removed in commit `9c99e755` (\"revert: remove tool permission rule system … Refs #438\") to simplify the user model.\n\n## Implementation Details\n\n### Frontend\n\n- **Checkbox UI**: `src/frontend/components/Chat/ChatInput.tsx` (props `requireApproval`, `onRequireApprovalChange`; lines ~52-53, ~88-89).\n- **Parent state & persistence**: `src/frontend/components/Chat/index.tsx` (useState line 575, hydration lines 1441-1448, change handler lines 1453-1461).\n- **Persist to server**: `src/frontend/services/chat/index.ts:333-343` → `PATCH /v1/chat/conversations/:id` with `{ requireApproval }`.\n- **Approval panel UI**: `src/frontend/components/Chat/ChatMessages.tsx` (lines 2137-2202 when `pendingToolCalls` is set).\n  - Shows tool name and formatted JSON arguments.\n  - Provides Approve and Reject buttons.\n  - No reason textarea is persisted.\n\n### Backend\n\n- **Conversation route**: `src/app/v1/chat/conversations/[conversationId]/route.ts`.\n  - GET line 219: `requireApproval ?? false` (default allow).\n  - PATCH lines 321-326: Boolean validation; stored in conversation settings.\n\n- **Runtime gate**: `src/backend/execution/flow/runFlow.ts` lines 684-2569.\n  - Line 684: `const requireApproval = input.requireApproval ?? false`.\n  - Lines 2525-2566: If `requireApproval=true`, pause execution and queue tool calls in `sharedState.pendingToolCalls` with status `'awaiting_tool_approval'`.\n  - Lines 2569-2595: If `requireApproval=false`, process all tools immediately via `processToolCallsRecoverably`.\n\n- **Approval decision**: `src/backend/execution/flow/resumeAfterApproval.ts` (issue #115).\n  - Approves or rejects a single tool call from the pending batch.\n  - Rejection always returns the fixed result `tool denied` (never custom feedback).\n  - Returns outcome `'ready'` when all pending calls are handled, `'awaiting'` when more calls remain.\n\n## Testing\n\nThe single-gate contract is locked by tests in:\n\n- `__tests__/flow/toolApprovalSingleGate.test.ts` — Verifies rejection returns `tool denied`, no permission rules exist, and single-gate semantics hold.\n- `__tests__/flow/requireApprovalDefault.test.ts` — Verifies the default is false and the gate properly distinguishes between approval-required and direct execution.\n- `__tests__/chat/applyApprovalDecision.test.ts` — Existing tests for the approval decision handler (issue #115).\n\n## Persona Behavior Snapshots (Out of Scope)\n\nA separate `Flow.behaviorRules` field is used only for immutable Persona / Enduring-Agent Behavior snapshots. It filters Persona-native abilities and questions and is unrelated to the ChatInput approval gate. It has no editor UI, no ChatInput linkage, and no persisted \"always\" decisions. Historical `permissionRules` JSON is accepted only as read compatibility; equal dual keys collapse to `behaviorRules`, conflicts are rejected, and new writes contain only the canonical key.\n\n## Future Redesign\n\nThe current single-gate model is intentionally minimal. A future redesign will define any additional authorization controls in a separate proposal, following first-principles design around a clear, minimal user model. Any future authorization controls must:\n\n- Preserve the ChatInput checkbox as the single, obvious approval gate.\n- Default to allow when approval is not enabled.\n- Avoid hidden folder, server, or tool defaults.\n- Avoid multiple overlapping policy layers.\n- Be explicitly reviewed against real user workflows before shipping.\n"
