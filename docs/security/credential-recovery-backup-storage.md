# Immutable encrypted core recovery backups

This source successor builds on #749's frozen object/manifest formats (`9eee0a650312ca9275cb767e040b63ba173b600f`). It adds encrypted filesystem persistence and authenticated inspection under a caller-held `WorkspaceRecoveryMutation`. There is no production caller or active-file replacement here. It does not install a pending marker, rotate a key, convert credentials, invalidate sessions/caches or expose an HTTP recovery operation. The full #567 migration and A- remain open.

`createCredentialRecoveryBackup` captures the five core files from the selected workspace's existing `db` using the unchanged bounded stable-descriptor reader. Only an initially absent file becomes a null original. A present file that disappears, changes identity/metadata, is not regular, has another hard link, exceeds bounds or fails canonical-parent/ownership policy refuses the backup. Original bytes are opaque, including invalid JSON or legacy binary content; active files are never parsed, repaired or modified by this helper. The trusted preparation caller must still prove actual source/target key IDs, a new random target key and complete authenticated record conversion. The different-ID manifest check is not that proof, and these five files exclude flows, bootstrap/runtime homes and other inventory required by #567.

Before the first asynchronous admission, the helper owns copies of the retained 32-byte recovery key and every supplied target buffer and captures the intent's scalar identity. Caller mutation during an await cannot substitute these values. Caller buffers and keys are not cleared. Owned originals, targets, key copies and readback plaintext are cleared in the preparation operation's finally paths; explicit inspection returns owned buffers and its caller must clear them. JavaScript strings, native crypto state and whole-process memory erasure are not qualified.

The fixed layout is `<workspace>/.credential-recovery/<UUIDv4>/`. Root/workspaces/workspace/db and the vault/transaction directories are checked as regular canonical directories, with retained parent identities rechecked throughout the operation. A vault can be reused only with its existing safe directory identity and private POSIX ownership/mode. Each transaction directory is created exclusively; existing complete or partial transactions are never overwritten or deleted. The fixed before/after filenames reveal core store names but contain only authenticated ciphertext. Recovery keys, secret values, content witnesses and source/target key IDs are not written in public sidecars.

Objects are created with `wx` and mode 0600, synced, and checked through the descriptor and named path for regular type, single link, dev/inode, exact size, nanosecond timestamps, mode and owner/group identity. The physical recovery lease and canonical directory ancestry are checked before effects and before acknowledgement. The encrypted manifest is written last, after all non-null before/after objects. Preparation then authenticates the manifest and every object, checks all private byte witnesses, refuses extra objects and re-reads current original files against the captured witnesses before acknowledging a prepared backup. Nothing in this acknowledgement authorizes active migration or a visible commit.

POSIX directory handles are synced and descriptor/named-directory identities are checked. Windows Node does not expose directory fsync; only file sync and authenticated readback are provided there. Windows ACL protection and power-loss durability need installed evidence. The existing native file identity guards are not relaxed for either platform. This registered-process protocol does not exclude arbitrary external or older unregistered writers, and Node path APIs do not provide a complete hostile-filesystem openat/renameat transaction.

Any interrupted write, lost ownership, altered original, malformed manifest, wrong key, role/file/transaction replay, missing object, extra object or witness conflict refuses acknowledgement with fixed diagnostics. Partial ciphertext is retained for explicit inspection; this helper does not automatically resume, delete objects, clear a gate or erase original data. A crash can leave incomplete ciphertext without a manifest, or complete ciphertext before successful readback. That is retained preparation evidence, not a committed active transaction. An explicit authenticated durable pending journal and commit/resume/rollback driver remain required.

Changed-file lint and diff checks pass. Nine newly authored source fixtures cover real native filesystem/crypto, complete opaque round trips, unchanged originals/caller key, encrypted persistence and caller cleanup, original absences/extra objects, interrupted preparation and no overwrite, wrong keys and role/file/transaction replay, valid-authentication witness conflict, hard-link denial, caller mutation during deferred admission, fixed refusals and workspace/directory prerequisites. They model exclusive process admission and have **not been executed locally** while Cloud holds the sole fixture slot. No assertion count, installed app, crash/restart, physical cross-process, Windows ACL, OCI, browser/provider or accepted-grade qualification is claimed. #749's separate 23-test codec/control receipt remains unchanged.
