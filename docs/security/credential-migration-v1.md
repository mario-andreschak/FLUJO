# Resumable credential migration

`/api/credential-migration` requires owner admin/secret authority, strict loopback access and a non-worker process. Encryption may be locked: preflight authenticates the explicit source passphrase (or existing legacy default/independent operator mount), and recovery authenticates the encrypted journal. Ordinary credential reads/writes and snapshot capture stay denied while a migration is pending.

POST JSON uses `action`, `sourcePassphrase` when applicable, `recoveryPassphrase` (16+ characters, at most 1,024 UTF-8 bytes, never the public legacy default), and optional `protection: passphrase | operator-file`. Operator protection requires the independently protected mount outside the data directory. The recovery passphrase protects the backup journal; retain it separately from the data files. It also becomes the target workspace passphrase for passphrase protection.

1. `action: preflight` returns store counts and a source-bound `planToken`, without changing source data or disclosing credential values.
2. `action: migrate`, that `planToken`, and `confirmMigration: true` prepare and authenticate all recognized model, registry, global environment and MCP credentials before publishing a private encrypted before/after journal. Source records are bounded to 5 MiB each and the complete encrypted journal plaintext to 32 MiB; oversized or corrupt records refuse preflight.
3. Replacements use authenticated v2 encryption and are read back for integrity. Migration from a public-default wrapper generates a fresh random active v2 data key and re-encrypts all supported live credential stores under it. A copied old public wrapper therefore cannot decrypt new live v2 ciphertext. Already privately protected v2 profiles retain their existing active key when changing protection. The legacy v1 read key is retained for compatibility; historical archives are not rewritten and rollback restores the exact original protection. This is not a claim that every historical copy or ciphertext outside the supported inventory has been rotated or deleted.
4. A pending journal is the logical transaction barrier. Files are atomically replaced individually while application credential access is denied. Only after every target byte and the authenticated journal are reverified does a single rename publish the committed state. This is an application transaction, not a multi-file filesystem atomic rename. POSIX parent descriptors are identity checked and synced. Windows process-interruption recovery is covered; Windows ACL privacy remains an operator responsibility.

GET returns only `{ pending }`. After interruption, POST `action: resume` or `action: rollback`, the recovery passphrase, and `confirmMigration: true`. All current files must match their exact recorded before/after hashes before any recovery replacement; unexpected changes refuse both operations and name only the affected store. Restore matching files from the encrypted journal or a trusted backup before retrying. Wrong passwords, tampering or invalid metadata leave the journal and data intact. Rollback restores the exact original bytes, including original key protection; unlock using the original profile afterward. A committed migration clears the cached unlock state; unlock with its target profile.

Journal and receipts request mode 0600. Committed/rolled-back encrypted receipts retain the exact source backup for recovery and have no automatic expiry or deletion. Preserve them until recovery has been verified, then remove only the explicitly identified receipt under operator-controlled retention. They are never ordinary backup selections. Source profile secrets and recovery passphrases must remain independently available; an encrypted receipt cannot replace a missing independent operator mount.

OAuth tokens, client information (including private JWKS/provider extensions), and PKCE verifiers use the runtime’s complete SDK envelope parser/serializer. Existing whole envelopes authenticate their purpose and source workspace; recipient transfer rebinds them to the new workspace before resealing. In-place migration preserves workspace binding and emits bare v2 ciphertext inside the canonical OAuth envelope. Legacy field-encrypted values remain recoverable. Invalid SDK records refuse migration and preserve source data. Existing MCP enablement is preserved by in-place migration; recipient transfers restore connections disabled for review.

Snapshot/bootstrap and historical exports are separate inventories. Snapshot capture refuses a pending migration; this operation neither rewrites existing immutable snapshots nor revokes already copied credentials. Source tests cover mixed v1/v2/plaintext, exact backup/rollback, interruption, corruption, real HTTP gates, independent operator mounts, separate OS-process resume/rollback/restart, and actual runtime OAuth getters. Installed-artifact, human and external acceptance remain unqualified by these Source tests.
