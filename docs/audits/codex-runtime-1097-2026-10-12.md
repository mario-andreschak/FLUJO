# Codex runtime and ordinary session qualification

This is the runtime/session batch of issue [#1097](https://github.com/mario-andreschak/FLUJO/issues/1097), based on main `d3e5c64ec52f08de16c221140d99d7ea788d80c5`.

Allowance, discovery and ordinary inference select the same leased executable.
Runtime receipts bind the CLI version/digest to the installed SDK and admitted
protocol/qualification contracts. Update probes cover bounded pagination,
received error framing and the SDK's public start/resume argument vectors. They
create no inference or tool turn and do not claim account entitlement.

Ordinary subscription conversations use separately owned app-server stdio.
Flow instructions retain developer authority; deltas preserve message identity;
the final answer is distinct from commentary. Steering targets the active turn
and acknowledges only acceptance. Uncertain submissions do not automatically
start a replacement turn or return a possibly accepted correction to the inbox.
Process birth admission, default rejection of server requests, and confirmed
closure remain required. Native Original/private and API-key SDK routes retain
their existing admission and execution policy.

Session compatibility now includes account/runtime/instruction/tool/configuration
identity and canonical history. Protocol totals persisted with session metadata
prevent counting earlier turns again after a registry reset. Latest-context,
cached input and reasoning output remain separate from accumulated usage.

## Question and reconnect batch

The ordinary app-server transport now handles both synchronous
`item/tool/requestUserInput` requests and the current asynchronous
`agentMessage.questions` shape. Questions use the existing attended executor,
approval policy and ownership fences. Asynchronous questions interrupt the
owned turn and require its matching terminal before a fresh dispatch check
allows the actual answer to continue. Decline, Stop, uncertain transport and
unresolved MCP effects do not submit an answer continuation. Ordinary startup
enables the computational code wrapper needed by the current model's offered
MCP tools while keeping native shell, agents and apps disabled; unknown native
requests still fail closed. Native Original/private policy is unchanged.

Bounded question and elicitation mailboxes provide workspace/conversation
snapshots for reload and SSE reconnection. Schema/cardinality errors retain the
prompt. Resolved, stopped, orphaned and cross-conversation responses are
rejected. A terminal run cannot restore or release a mailbox that is still
awaiting external cancellation after its tool deadline. Cancellation settles
the affected question and approval exactly once;
resource retirement still requires authoritative owned-child closure.

## Compressed rollout and SDK accounting maintenance — October 13

This focused batch starts from main `5b061100ddce08522ca7512e86db2cd90da660b6`.
The pinned upstream [compression implementation](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/rollout/src/compression.rs)
writes standard Zstandard `.jsonl.zst` files, prefers a plain sibling and
materializes plain JSONL before append. The pinned [exec JSON event processor](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/exec/src/event_processor_with_jsonl_output.rs)
emits cumulative thread usage in `turn.completed`. An unavailable baseline
therefore cannot establish the current invocation's token count.

The reader resolves plain/compressed/materialized representations on every
cached lookup, retries a bounded rename race and validates regular files and
parents before reading an opened descriptor. Discovery is bounded; compressed
input and retained decoded tail are each limited to 8 MiB, total decoded output
to 64 MiB, and the native decoder window to 8 MiB. Invalid, incomplete or
over-budget archives yield unknown. Node `22.23.3` provides the native streaming
decoder; the existing dependency/runtime requirements are unchanged. Rollout
transcript content is never returned by this reader.

The narrowly coordinated SDK fallback guard subtracts a complete, same-thread,
monotonic baseline and validates token subsets. Missing, corrupt, oversized,
incomplete or regressed baselines, inconsistent counters and a changed captured
thread omit `completion.usage`; known current context and the answer survive.
First-turn known usage retains its existing mapping. Ordinary app-server and
Native Original/private accounting and admission are unchanged.

- All 104 focused cases across the reader, compressed reader and adapter passed.
  Caller regressions use actual compressed files and cover the 20-input/4-output
  increment, all eight unknown-baseline/identity cases, retained context/output and
  first-turn mapping. Existing live-write and descriptor-boundary cases remain.
- Supervision reproduced a stale plain baseline: valid older 10/2 followed by a

  previously skipped the invalid event while compressed storage returned unknown,
  allowing a fabricated 20/4 increment from SDK cumulative 30/6. The final reader
  rejects completed invalid token events in both representations, including a

  event during an incomplete final plain write. Reader equivalence and resumed
  caller regressions preserve this distinction; the negative remains in the
  sanitized receipt.
- Actual shipping CLI/SDK `0.162.1` started a thread in a newly isolated home,

  through SDK exec. Its standard `28b52ffd` frame decoded byte-exactly; resume
  materialized plain before append and removed the compressed sibling. The old
  reader returned unknown on that shipping-produced frame; this negative is
  retained separately.
- The final production reader/helper recovered baseline 10 input/2 output,

  The [sanitized receipt](evidence/codex-context-1097-2026-10-13/storage-runtime.json)
