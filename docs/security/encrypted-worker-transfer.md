## Sender and recipient contract

Before capture, the recipient generates 32 cryptographically random bytes and retains that key independently of the archive. It sends canonical base64 in `recipientKey` to the existing authenticated loopback `POST /api/snapshot/begin`, optionally with `flowIds`. Missing, malformed or wrong-length keys receive a fixed 400 response before session reservation, credential capture or archive staging. This input establishes key possession; the source cannot verify randomness or independent retention from a 32-byte value alone. The transfer client must enforce those operational properties.

The source encrypts the complete compressed ZIP in memory using AES-256-GCM, a fresh 12-byte nonce and AAD `flujo:workspace-snapshot:v2`. The only newly persisted archive is UTF-8 JSON with exactly `format`, `version`, `iv`, `tag` and `data`. The format is `flujo-workspace-encrypted`, version is 2, and the remaining fields are canonical base64. Neither the bootstrap key nor recipient key appears as a separate archive field. The compressed plaintext buffer and owned key buffers are cleared after their use. This is not a guarantee that every prior JS object, SDK value or immutable request string has been erased from process memory.

Session/status responses identify `encryptionVersion: 2` and omit the recipient key. Download uses `application/vnd.flujo.workspace-snapshot+json`, an `.encrypted.json` filename, `no-store`, `nosniff`, and the existing length/SHA-256 headers. Reported size and SHA-256 refer to the encrypted wire bytes. Legacy live-session records lacking version 2 refuse download; a new session is required.

The recipient stores those exact bytes and supplies their digest as `FLUJO_WORKER_SNAPSHOT_SHA256` and its separately retained key as `FLUJO_WORKER_SNAPSHOT_KEY`. Worker restore authenticates the envelope and verifies the wire digest before ZIP inspection, manifest validation, extraction or workspace writes. A missing/wrong key, corrupt tag/nonce/ciphertext, format/version substitution or digest mismatch refuses restore. Fixed diagnostics omit raw crypto/parser causes. Existing ZIP entry, size, manifest, link and destination checks still apply.

Existing v1 bridge envelopes remain readable with their historical plaintext-ZIP digest contract. Historical raw ZIP restores remain readable without an envelope key. These are compatibility reads; new source snapshot writes produce only v2. Version 2 uses AAD so changing its version to 1 does not create an accepted downgrade.

Its present begin request supplies no recipient key, so this source rejects it before capturing credentials. It must generate the random key before begin, include `recipientKey` in the JSON body, require `encryptionVersion: 2`, and preserve the returned encrypted bytes and digest through staging and restore. It must stop wrapping the downloaded bytes in a second envelope. Its existing secret-input transport, owned file permissions, acknowledgement, key clearing and cleanup contracts still require qualification by the cloud owner. No cloud repository files are changed or qualified by this FLUJO slice.

Archive staging continues to request mode 0700 for the temporary directory and 0600 for the archive. Native Windows ACL confidentiality is not proved by POSIX mode arguments. Finalize/abort/expiry use the existing owned-session cleanup. The route composition fixture observes the directory absent after successful finalize; this does not qualify every interruption, crash or failed cleanup. The recipient/cloud owner controls retention and recovery of the separate key and downloaded archive. This change supplies no migration rollback protocol.
