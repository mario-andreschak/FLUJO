# Worker image snapshot restore contract

This narrow successor starts at #740, `69736140a70ad76068c8f52531c1d5944611e97e`. It adds explicit runtime-image labels for encrypted restore versions and default acceptance limits. It does not change manifest format 2, workspace layout 2, worker protocol 1 or the existing authenticated `workerCompatibility.snapshotEncryption.readVersions: [1, 2]` field. The source contract remains [snapshot capability and acceptance limits](snapshot-capability-contract.md).

The proposed immutable image labels are:

| Label | Exact value |
| --- | --- |
| `io.flujo.worker.snapshot-envelope-read-versions` | `1,2` |
| `io.flujo.worker.snapshot.restore.limits` | `{"maxFileBytes":268435456,"maxUncompressedBytes":1073741824,"maxManifestBytes":8388608,"maxArchiveBytes":1082130432,"maxEncryptedBytes":1442844672,"maxMembers":65534}` |

The first value is the canonical comma-separated encrypted-envelope read-version list. Require the exact supported contract and version 2; an absent label, version 1 alone, app version, worker protocol or manifest format is insufficient. The second is canonical JSON containing all six default restore acceptance bounds, with positive safe integers. It describes the unmodified image defaults, not a runtime with environment overrides or a memory budget. `scripts/snapshot-image-contract.mjs` exports the exact limits string used by image inspection and worker publication.

Before capturing credentials, the companion must qualify both the authenticated source advertisement and its separately selected official immutable target image. Bind target version/limits labels to the actual configuration digest, official source identity, full build revision and qualification evidence. Retain every existing image check, including the combined root's `io.flujo.worker.snapshot-source="1"` private-source discriminator and corresponding source consent/lease protections. These are additional requirements; a source info response does not qualify a different target image. Arbitrary caller-supplied labels or a mutable image tag do not establish provenance or successful restore.

Compare all source `snapshotLimits` fields to the separately qualified target limits before begin. A larger source bound requires a qualified target configuration or refusal before capture; do not assume successful capture implies target acceptance. Preserve the independent recipient key, exact v2 wire bytes and wire SHA-256 contracts. Limits must remain bound to the selected image throughout provisioning and restore. Any target limit override needs separate proof of its effective values; these default labels cannot qualify it.

The Dockerfile declares both labels. The image release inspector checks them on fresh configuration inspection, reuse and registry readback; evidence validation rejects their absence before promotion/signature/registry calls. Worker publication checks them before the offline smoke for both a fresh image and reuse of an immutable revision. The installed worker smoke independently compares authenticated effective restore limits to the declared default contract while exercising v2 encrypted restore, real synthetic engine/MCP execution and restart preservation. This smoke has not run for this successor; no image was built, published or deployed here.

Selected source fixtures compare the Dockerfile read-version list to the actual native encryption capability and its limits JSON to `getSnapshotLimits()` with both overrides removed. Image tests compare the Dockerfile to the exported limits string, execute the workflow's actual fresh-image validation code against synthetic inspection JSON and reject missing/wrong version and bounds labels. Modeled candidate/promotion controls assert zero registry mutation on refusal. These do not qualify Docker label parsing, installed private credential transfer or a deployed image. The existing cryptographic and authenticated route fixtures exercise real v2 encryption/decryption and advertised wire metadata.
